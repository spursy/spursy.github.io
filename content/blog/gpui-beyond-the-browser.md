> "Are we GUI yet?" 最初是 Rust 社区的追问。桌面开发者长期纠结同一件事：**既想要现代 UI 的开发效率，又不想为此接受 Electron、Tauri 这类 Web 方案在性能和架构上的妥协。** 这篇把这条矛盾讲透——从浏览器渲染流水线的原理说起，一路走到 GPUI 的帧流水线，再到 gpui-kit 如何让这条路真正可走。

## 一、Electron 与 Tauri：它们怎么实现，又卡在哪

两者都要解决同一个问题：**让开发者用 HTML/CSS/JS 写跨平台桌面界面**。但实现路线不同。

```
 Electron (2013)                      Tauri (2019)
 ┌─────────────────────┐             ┌─────────────────────┐
 │  自带整份 Chromium    │             │  用系统自带 WebView   │
 │  Blink  +  V8        │             │  WKWebView / WebView2 │
 │  + Node.js 后端      │             │  + Rust 后端          │
 └─────────────────────┘             └─────────────────────┘
   体积大 · 一致 · 可控                 体积小 · 轻 · 各平台不一致
```

先厘清两个常被混的概念：

- **Chromium** 是 Google 的开源浏览器引擎（Blink 渲染 + V8 跑 JS），**可以整个打包进你的应用一起发货**。
- **WebView** 是「嵌在原生应用里的网页控件」。**系统 WebView** 由操作系统提供：macOS 是 WKWebView(WebKit)、Windows 是 WebView2(Chromium)、Linux 是 WebKitGTK。

| | Electron（打包 Chromium） | Tauri（系统 WebView） |
|---|---|---|
| 引擎来源 | 应用自带一整份 | 用系统现成的 |
| 体积 | 大（100MB+） | 小（几 MB） |
| 跨平台一致性 | 高（到处同一份引擎） | 低（各系统引擎不同） |
| 版本控制权 | 开发者 | 操作系统 |

**为什么 Electron 当年选打包 Chromium？** 2013 年根本没有像样的系统 WebView（WebView2 要到 2020 年才出现），想在三端都拿到现代、一致的引擎，只能把 Chromium 整个带走。**Tauri 为什么选系统 WebView？** 2019 年三大系统都有了现代 WebView，于是用它换体积、内存和安全，代价是跨平台不一致。

但无论哪条，都共享同一个根本前提：**UI 层是一个浏览器**。它们的局限都从这里来，而要讲清这个局限，必须先看浏览器是怎么把 HTML/CSS 变成像素的。

## 二、浏览器渲染流水线：Style → Layout → Paint → Composite

每一帧，浏览器都要把「DOM + CSS 的描述」变成「屏幕上的像素」，走的是一条单向流水线：

```
  JS 改 DOM / 样式
        │
   ① Style     计算每个元素最终长什么样（颜色/字号/边框…）
        │
   ② Layout    算每个元素放哪、多大（= reflow 回流）
        │
   ③ Paint     把每个元素画成绘制指令/位图（= repaint 重绘）
        │
   ④ Composite 把图层在 GPU 上拼成最终一帧
        │
      屏幕
```

逐步拆解每一步在干什么、解决什么问题：

### ① Style（样式计算）

浏览器拿着 DOM 和所有 CSS 规则，为**每个元素**算出它「最终生效的样式」（computed style）。因为 CSS 有层叠、继承、选择器优先级、`!important`，同一个属性可能被多条规则命中，必须收敛出唯一值。

- **解决的问题**：把「一堆分散、可能冲突的 CSS 规则」收敛成「每个元素一份确定的样式」。
- **代价**：元素多、选择器复杂时，选择器匹配不便宜。

### ② Layout / Reflow（布局 / 回流）

根据样式算出**每个元素的几何信息——位置(x/y)和尺寸(宽/高)**。

- **解决的问题**：CSS 里大量尺寸是相对的（`width:50%`、`flex:1`、`auto`、文字折行后撑多高），必须现场把「相对描述」解成「绝对坐标」。
- **为什么最贵**：它会**连锁**。改一个元素的宽度，可能让它的子元素、兄弟元素乃至整页重排。读 `offsetHeight`、`getBoundingClientRect()` 还会**强制同步回流**，用不好直接卡。

### ③ Paint / Repaint（绘制 / 重绘）

知道了「在哪、多大」之后，决定**每个像素填什么颜色**——把文字、背景、边框、阴影、渐变画成一条条绘制指令，通常分若干图层。

- **解决的问题**：把「几何骨架」填成「可见内容」。
- **代价**：比 Layout 便宜些，但阴影、模糊、复杂渐变会让它变重。只改颜色/背景这类**不影响几何**的属性，只触发 Paint，跳过 Layout。

### ④ Composite（合成）

把画好的**多个图层在 GPU 上拼成最终一帧**，并应用 `transform`、`opacity`、层级叠放。

- **解决的问题**：把易变元素放进独立图层，它动时**只在合成阶段挪一下图，不必重新 Layout/Paint**，极省；拼合、位移、透明度混合这些 GPU 做得飞快。
- 这也是为什么前端做动画偏好 `transform/opacity`——走最便宜的合成路径。

这三样具体是：**`transform`**（位移 / 缩放 / 旋转元素，但**不改变它在布局里占的格子**——周围元素不会因此重排）、**`opacity`**（整体透明度，0 透明、1 不透明，淡入淡出靠它）、**层级叠放**（用 `z-index` 决定重叠时谁盖在谁上面，弹窗 / 下拉能浮在正文之上就是它）。它们的共同点是：**只摆放和混合「已经画好的图层」，既不碰几何(Layout)也不碰像素(Paint)**——而「挪图、透明度混合、按序叠放」恰是 GPU 最拿手的事。所以这里有一条前端动画铁律：**用 `transform` 位移而不是改 `left/top`，用 `opacity` 淡出而不是改 `display`**——前者只走合成、丝滑不掉帧，后者会触发 Layout 回流、容易卡。

把这条链的「代价梯度」记住：

| 你改了什么 | 要走哪几步 | 代价 |
|---|---|---|
| 位置/尺寸/增删节点 | Style → **Layout** → Paint → Composite | 🔴 最贵 |
| 颜色/背景/阴影 | Style → ~~Layout~~ → Paint → Composite | 🟡 中等 |
| `transform` / `opacity` | 只走 **Composite** | 🟢 最便宜 |

**这就是 Electron/Tauri 的性能天花板来源**：这条流水线是为「渲染任意文档」设计的通用机制，每帧都要做「样式收敛 + 几何推算 + 分层绘制」。内容一复杂（万行表格、实时 K 线），Layout+Paint 很容易吃光一帧的预算；再叠加 JS 单线程 + GC 停顿，就一卡一卡。架构上还有第二刀：**前端(JS)和后端(Node/Rust)是两套世界，中间隔着一道 IPC 序列化边界**，数据量大时既慢又把代码劈成两半。

问题的根不在「哪个框架烂」，而在**都把浏览器当 UI 层**。那——能不能不用浏览器？

## 三、GPUI 是什么，它怎么工作

**GPUI 是 Zed 编辑器团队用 Rust 写的 GPU 加速 UI 框架。** 它的根本区别只有一句：**里面没有浏览器**——没有 DOM、HTML、CSS、JS，也没有 WebView，直接用 GPU 把界面画出来。

几个关键特征：

1. **直接画到 GPU**：文字、形状、图片、渐变全由 GPUI 自己用 GPU 绘制（macOS 走 Metal、Windows 走 Direct3D、Linux 走 Vulkan 一类）。
2. **一种语言打通到底**：UI 和业务逻辑都是 Rust，**没有前后端语言切换，也没有 IPC 序列化边界**，UI 直接读写同一份内存里的数据。
3. **混合渲染模型**：借鉴立即模式——每帧根据状态重建元素树，但配合实体(entity)系统管理状态，布局用类 Flexbox 引擎 taffy。
4. **Rust 底子**：无 GC、可真并发。

### 帧流水线：GPUI 的一帧怎么走

> 阶段名随 GPUI 版本略有变化（早期 `layout`，后来拆成 `request_layout` / `prepaint` / `paint`），下面讲稳定不变的那套思路。

```
  状态变化 → cx.notify() 把某个 View 标脏（没变化就不画）
        │
   ① render()       被标脏的 View 重建一棵「用完即弃」的元素树
        │            （样式写死在 Rust 方法链里，没有 CSS 层叠要收敛）
   ② request_layout 把 flexbox 样式喂给 taffy
        │
   ③ taffy 计算      一次解出每个元素的 x/y/宽/高
        │
   ④ prepaint       几何已知，登记 hitbox / 裁剪 / 延迟浮层
        │
   ⑤ paint          每个元素生成 GPU 图元，塞进一个扁平的 Scene
        │            （quad / 字形 / 图片 / 路径）
   ⑥ GPU 光栅化      Scene 合批提交给 GPU，一把算出这一帧几百万像素
        │
      屏幕（再被标脏才重走）
```

### 为什么这条流水线从「状态变化」开始

第一次看这张图，最容易卡在起点：**为什么不是从「画」开始，而是从「状态变化」开始？** 答案藏在一个所有现代 UI 框架（React、SwiftUI、GPUI）共享的核心公式里：

> **UI = f(state)** —— 屏幕上显示什么，是「当前状态」的一个函数。状态是输入，画面是输出。

这句话的含义是：**你永远不直接操作画面，你只改「状态」，画面只是状态的倒影。** 价格变了，老式(命令式)写法要手动找到那个文本控件 `label.setText("229")`；声明式写法只改数据 `stock.price = 229`，画面由框架自己重算。于是**一帧的唯一起因，就是「状态变了」**——没有数据变化，这一帧就该和上一帧一模一样，根本不必重画。整条流水线本质在回答一个问题：**状态变了，新画面长什么样？**

那「状态」是什么、怎么变？状态就是应用持有的数据，存在 GPUI 的实体(entity)里。拿行情场景举例：一个自选股列表的状态可能是 `stocks = [{AAPL, 228}, {TSLA, 410}]`、`selected = "AAPL"`。它从不自己变，总是被某个外部事件改的——就三类来源：

| 来源 | 例子 | 改了什么状态 |
|---|---|---|
| 用户输入 | 点一只股票 / 按 ↓ / 打字 | `selected = "TSLA"` |
| 外部数据 | 服务器推来一条行情 | `stocks[0].price = 229` |
| 时间 / 定时器 | 动画推进、每秒刷新 | 某个进度值 +1 |

而「怎么变」就是一句普通的 Rust：

```rust
self.stocks[0].price = 229;  // ① 改数据：状态在这里变化
cx.notify();                 // ② 标脏：告诉框架「我这块变了，该重画」
```

注意第二行 `cx.notify()` **不是去画，而是打个「脏(dirty)」标记**。为什么不立刻画？因为立刻画是浪费——一帧内若连来 3 条推送，「每改一次画一次」就白画 2 次。GPUI 的做法是：**状态变化时只标脏，不立刻重画；等到下一个渲染时机，才去看哪些 View 是脏的、只重画它们，没标脏的整块跳过（连 `render` 都不调用，直接复用上一帧）。** 这就是图里那句「没变化就不画」，也是 GPUI 高效的核心：**变化驱动渲染，而不是无脑每帧全画。**

想通了这个起点，后面六步就是把「脏了的那块」重新算成像素的流水线。逐个关键词看：

- **① render() → 元素树**：被标脏的 View 跑 `render()`，产出一棵用嵌套元素描述「这块长什么样」的**元素树**。它**每帧新建、画完即弃**（立即模式的味道），不像 DOM 那样长期留存再 diff——因为是 Rust，重建很便宜。样式直接写死在 `.bg().padding()` 这样的 **Rust 方法链**里，没有 CSS 层叠要收敛。
- **② request_layout + ③ taffy**：把每个元素的 **flexbox** 样式（横排竖排、占多宽、间距）喂给布局库 **taffy**，由它一次性解出每个元素的 x/y/宽/高。对应浏览器的 Layout，但是个干净的专用求解器。
- **④ prepaint**：几何已知后做三件「必须知道确切位置才能干」的事——登记 **hitbox**（命中区域，鼠标点下来才知道点的是谁）、**裁剪**（把内容限制在容器边界内，圆角 / 滚动靠它）、**延迟浮层**（下拉 / 弹窗登记到最上层，等正文画完再叠上去）。
- **⑤ paint → 图元 + Scene**：把每个元素翻译成 GPU 能懂的**图元**——**quad**（带圆角 / 边框 / 阴影的矩形）、**字形(glyph)**、图片、路径，全平铺进一个叫 **Scene** 的扁平清单，相当于「这一帧的施工图纸」。到这步为止全是 CPU 在用 Rust 干活，还没出一个像素。
- **⑥ GPU 光栅化**：把 Scene 交给 GPU，同类图元**合批**后一次提交，GPU 用几千个核把这一帧几百万像素并行**光栅化**出来（见下一节）。画完上屏，流水线停住，直到状态再次变化、某个 View 再被标脏。

一句话串起来：**用户点一下 / 行情推一条 → 改一份数据（状态变化）→ `cx.notify()` 标脏 → 到渲染时机只对脏的 View 重建元素树 → taffy 定位 → prepaint 登记交互 → paint 译成图元进 Scene → GPU 合批光栅化成像素 → 上屏 → 停住等下次变化。** 核心就一句：**状态是因，画面是果。**

### 它是如何「替换掉」DOM/CSS 流水线的

把两条流水线逐段并排，就能看清 GPUI 做了什么减法：

| 浏览器流水线 | GPUI 帧流水线 | 关键差异 |
|---|---|---|
| **Style**（层叠样式计算） | **几乎没有** | 样式写死在 Rust 方法链里，没有 CSS 选择器/层叠要收敛——**整步砍掉** |
| **Layout / reflow** | `request_layout` + **taffy 计算** | 同是 flexbox 求解，但专用、无文档包袱、**无强制同步回流的坑** |
| （无单独对应） | **prepaint** | 几何已知后登记 hitbox / 裁剪 / 浮层 |
| **Paint / repaint** | **paint**（生成图元进 Scene） | 直接产出 GPU 图元，而非分层位图 |
| **Composite**（维护长期图层树） | **Scene → GPU 合批光栅化** | 不维护持久图层树，每帧把扁平图元整个交 GPU 重画，靠 Rust+GPU 够快 |
| DOM（长期保留 + 增量改 + React 再 diff） | **元素树每帧重建、用完即弃** | 没有 DOM，也不 diff；重建很便宜因为是 Rust |
| JS 运行时 + GC | Rust，无 GC | **不会有某帧被垃圾回收随机打断** |

**本质区别**：浏览器为了「能渲染任意文档」背了一条通用重流水线；GPUI 把它压成「render 重建元素树 → taffy 布局 → 生成图元 → GPU 光栅化」，**省掉样式层叠和持久合成层**，用 Rust 无 GC + GPU 合批，把每帧预算守得更稳。于是前面 Electron/Tauri 的每条取舍都被对上了：

| Web 方案的取舍 | GPUI 的做法 | 结果 |
|---|---|---|
| DOM/CSS 渲染开销、掉帧 | GPU 直绘，无 reflow/repaint 那套 | 轻松 60/120fps |
| JS 单线程 + GC 卡顿 | Rust 无 GC、可真并发 | 无 GC 停顿 |
| Chromium 体积大、启动慢 | 没有浏览器引擎 | 体积小、启动快、省内存 |
| 前后端两套世界 + IPC 边界 | UI 与逻辑都是 Rust，共享数据 | 没有序列化边界 |
| WebView 跨平台不一致 | 界面自己画 | 两端像素级一致 |

## 四、60/120fps、GPU 为什么快、gpui-kit 怎么调用 GPU

### 60/120fps 指的是什么

**FPS = 每秒画多少帧。** 界面不是连续动，而是一帧帧静态画面快速连播。这个数字对应屏幕刷新率：

- **60fps** → 每帧只有约 **16.7ms**（1000÷60）来「算布局 + 画好这一帧」；
- **120fps** → 每帧只有约 **8.3ms**（高刷屏、ProMotion）。

关键不在「平均帧率高」，而在**每一帧都不能超时**：一帧没在预算内画完，就会掉帧(jank)，就是滑动时那种一顿一顿的感觉。所以「支持 60/120fps」= 承诺**再复杂的界面，每帧也压在 8.3/16.7ms 内**。

### GPU 为什么可以那么快

画屏幕的本质是「**把矢量图形变成一个个像素**」，这一步叫**光栅化(rasterization)**：遍历图形覆盖到的像素，逐个决定颜色。而一块屏幕几百万像素、每个像素「该填什么色」基本是**同一种独立计算**——这正是 GPU 的主场。

先把光栅化看懂。屏幕是一张**像素网格**——几百万个只能显示一种颜色的小方块；可代码里描述图形用的却是**矢量**语言：「从 (10,10) 到 (110,60) 画一个蓝色圆角矩形」「在这里放一个字母 A」，里面根本没有「像素」。光栅化就是在两者间翻译，**逐像素**地问两个问题：**①这个像素被形状盖到了吗？**（覆盖判定，比如圆角处那几个像素在不在圆弧内）**②若盖到了，该是什么颜色？**（纯色直接填，带渐变/透明/纹理就算混合色）。边缘还要做**抗锯齿**：形状边界很少正好压在格子线上，于是边缘像素填一个「半蓝半白」的过渡色，斜线和圆角才平滑、不呈锯齿状阶梯。最典型的例子是**画一个字**：字体文件里「A」是几条贝塞尔曲线描的轮廓，光栅化就是把这轮廓「填」进像素网格——轮廓内点黑、轮廓外点白、压在边上的点填灰。你屏幕上每个字，本质都是这样被光栅化出来的一小片像素。

它为什么天生适合 GPU？因为**每个像素的颜色互相独立**——像素 A 是什么色，不依赖像素 B 的结果。这种**海量、同质、互不依赖**的计算，正好是 GPU 擅长的：

| | CPU | GPU |
|---|---|---|
| 核心数 | 几个~几十个强核 | 几百~几千个弱核 |
| 擅长 | 复杂逻辑、串行 | **同一操作，同时对海量数据做** |
| 比喻 | 几个博士解难题 | 几千个小学生同时算加减 |

把「填几百万像素」从几个 CPU 核搬到几千个 GPU 核上并行，于是又快又能稳住高帧率。这就是「GPU 加速」四个字的全部含义。

### gpui-kit 怎么调用 GPU

GPUI / gpui-kit 不直接碰硬件，中间有一条链：

```
 gpui-kit 的组件
      │ 生成元素树 → taffy 布局 → 产出 Scene（扁平图元列表）
      │ 以上在 CPU 上用 Rust 跑
      ▼
 图形 API：Metal(macOS) / Direct3D(Windows) / Vulkan(Linux)
      │ 通过
      ▼
 GPU 驱动 → GPU 硬件 → 光栅化出像素 → 屏幕
```

具体地：前五步（`render` 建树、`taffy` 布局、生成 `Scene`）主要在 **CPU** 上做；真正让 GPU 出场的是第六步——把 Scene 里成千上万个 **quad（带圆角/边框/阴影的四边形）、字形(glyph)、图片** 按类型**合批**，经 Metal/Direct3D/Vulkan 提交给 GPU，由它用 shader 把这一帧并行光栅化。文字和 SVG 会被**事先渲染进 GPU 纹理图集(texture atlas)并缓存**，重复使用时不再重算。这就是 gpui-kit 在你机器上（Mac 是 M 芯片集成 GPU，PC 可能是独显）稳住 120fps 的硬件底气。

## 五、GPUI 的困局：省掉浏览器，等于要重造一切

天下没有免费的午餐。**GPUI 抛弃浏览器的代价，就是浏览器几十年白送的一切，都得从零重造。** 用 GPUI 画页面之前，要先铺好一座基建金字塔：

```
   ┌──────────────────────────────────┐
   │ 组件库（画页面的真正起点）            │  ← 这一层最缺
   ├──────────────────────────────────┤
   │ 状态/响应式 · 动画 · 资源管理          │
   ├──────────────────────────────────┤
   │ 无障碍 · 剪贴板 · WebView · 跨平台     │
   ├──────────────────────────────────┤
   │ 文本输入（IME 中文 · 选区 · 撤销 · 映射）│
   ├──────────────────────────────────┤
   │ 浮层与层级（Popover · 延迟渲染）        │
   ├──────────────────────────────────┤
   │ 交互（事件 · 焦点 · 键盘 · 滚动 · 裁剪）  │
   ├──────────────────────────────────┤
   │ 文本（整形 · CJK 断行 · 回退 · 光栅化）   │
   ├──────────────────────────────────┤
   │ 窗口 · GPU 后端 · 图元 · 布局 · HiDPI    │  ← 没它一个像素都画不出
   └──────────────────────────────────┘
```

这座塔自底向上，每一层都是浏览器默默替你扛了、而自绘必须自己铺的活：

- **① 窗口 · GPU 后端 · 图元 · 布局 · HiDPI**——最底的地基。要自己开窗口、对接 Metal/Direct3D/Vulkan，定义 quad/字形这些**图元**，接一个布局引擎(taffy)，还要处理**高分屏(HiDPI)**的缩放——没有这层，连一个像素都画不出来。
- **② 文本（整形 · CJK 断行 · 回退 · 光栅化）**——「画一行字」远没想象中简单。**整形(shaping)**：把字符按字体规则排成字形并处理连字、组合;**CJK 断行**：中文没有空格，得自己判断一行到哪里能换;**字体回退(fallback)**：当前字体缺某个字(如 emoji 或生僻字)要自动换一个字体顶上;最后把字形**光栅化**成像素。这一摊是桌面开发最容易低估的深坑。
- **③ 交互（事件 · 焦点 · 键盘 · 滚动 · 裁剪）**——鼠标点到哪个元素(命中测试)、Tab 在控件间怎么移焦点、键盘快捷键分发、滚动容器、以及把超出边界的内容**裁剪**掉。这些「理所当然」的行为，全要自己实现一遍。
- **④ 浮层与层级（Popover · 延迟渲染）**——下拉菜单、tooltip、对话框必须浮在正文**最上层**，还要能超出父容器边界。这要靠**延迟渲染(deferred)**：正文先画，浮层记下来最后叠上去（就是帧流水线 prepaint 那步登记的东西）。
- **⑤ 文本输入（IME · 选区 · 撤销 · 映射）**——不只是 IME，还有鼠标拖**选区**、`Ctrl+Z` **撤销栈**、把按键**映射**成编辑命令。一个真正能用的输入框，背后是一整套文本编辑基建。
- **⑥ 无障碍 · 剪贴板 · WebView · 跨平台**——无障碍(下面细说)、系统**剪贴板**读写、必要时内嵌一块 **WebView**(比如渲染富文本邮件)、以及把上面每一层都在 **macOS / Windows / Linux** 三个平台对接一遍并保证像素一致。
- **⑦ 状态 / 响应式 · 动画 · 资源管理**——`cx.notify()` 标脏那套**响应式**机制、流畅的**动画**、图片字体等**资源**的加载与缓存。
- **⑧ 组件库**——金字塔的塔尖，也是**画页面真正的起点**。前面七层全铺好，你手里也只有「一块能画像素、能输入、能响应的画布」，离「拖一个 Button 出来就能用」还差了整整一层**现成组件**。而这层恰恰最缺。

越底层越是硬门槛。其中两根最痛的刺，值得单独拆开看。

#### 刺一：IME —— 中文输入

**IME（输入法编辑器）是「把一串按键翻译成最终字符」的那层系统软件。** 英文按 `a` 就出 `a`，几乎用不上它；但中文、日文、韩文字符量巨大、没法一键一字，全靠它。你以为「打字 → 出字」是一步，其实中间夹着一整套交互：

```
   你按下: n i h a o
        │
   ┌────▼──────────────────────────┐
   │ 系统输入法（微软拼音 / 搜狗 …）     │
   │  ① 把 "nihao" 显示成带下划线的    │  ← 预编辑(preedit / 组字串)
   │     拼音串，悬在光标处             │
   │  ② 弹出候选词窗：1.你好 2.拟好 …   │  ← 候选框(candidate window)
   └────┬──────────────────────────┘
        │ 你按空格 / 数字选中「你好」
        ▼
   最终把「你好」commit 进输入框
```

对框架来说，这里有几件**必须亲自配合**、而浏览器 `<input>` 已替你全办好的事：把那串「还没定下来的拼音」画在光标正确位置并随输入实时更新；把**光标的屏幕坐标**喂给操作系统，好让候选框精准弹在光标下方；处理组字中途的退格 / 移动光标；只有最终选定才 commit 进文本。少了这层，表现就是**中文根本打不进去，或候选框乱飘、拼音串不显示**——这正是许多早期自绘框架「英文能用、一上中文就废」的原因。GPUI 要服务中日韩用户，就得把 macOS 的 `NSTextInputClient`、Windows 的 TSF、Linux 的 IBus/Fcitx 这几套系统 IME 协议逐一对接，是实打实的苦工。

#### 刺二：无障碍 / Accessibility

**无障碍是「让看不见、听不见、用不了鼠标的人也能操作界面」的一整套能力。** 核心在于：残障用户不是用眼睛「看」界面，而是通过**屏幕朗读器**（macOS 的 VoiceOver、Windows 的 NVDA）把界面「读」成语音。而朗读器读不懂像素，它需要一份**平行的语义描述**——一棵**无障碍树(Accessibility Tree)**：

```
   视障用户按 Tab 跳到一个按钮
        │
   屏幕朗读器问系统：这里是什么？
        │
   ┌────▼───────────────────────┐
   │ 无障碍树（界面的「语义副本」）     │
   │  按钮「买入」· 可点击 · 当前聚焦  │
   └────┬───────────────────────┘
        │ 朗读器读出：
        ▼
   「买入，按钮」→ 用户听到，知道按空格能下单
```

**浏览器**里你写 `<button>买入</button>`，它**自动**生成这棵语义树交给系统；**GPUI 自绘**时，屏幕上只有它画的像素，**操作系统根本不知道那块发光区域是个「按钮」**，于是框架必须亲手为每个控件维护语义节点（这是按钮、文字是「买入」、可聚焦），组成无障碍树，再通过金字塔里提到的 **AccessKit** 翻译成各平台的无障碍协议。少了它，**读屏扫过去一片空白，盲人用户完全没法用**；而在美国 Section 508、欧盟 EAA 等法规下，无障碍还是**能否进企业 / 政府市场的硬门槛**，不是锦上添花。

两根刺的共同点一目了然：

| 能力 | 浏览器（Electron/Tauri） | GPUI 自绘 |
|---|---|---|
| **IME 中文输入** | `<input>` 自带，全平台 IME 协议已对接 | 自己对接 macOS / Windows / Linux 三套系统 IME |
| **无障碍** | HTML 标签自动生成无障碍树 | 自己为每个控件维护语义节点（靠 AccessKit） |

再加上生态困局：会 GPUI 的人少，没有 npm 那样海量的现成组件。结果就是——**GPUI 很美，但几乎「只有 Zed 用得起」**。谁来把这座金字塔铺成普通团队能用的地基？

## 六、gpui-kit：把困局填平的那一层

**gpui-kit 就是答案。** 它由 Longbridge 桌面客户端的真实场景驱动，始终跟随 GPUI 的 `main` 分支：**真实产品发现问题 → 在实际代码里验证改进 → 把通用成果回馈开源**，形成闭环。

### 它是怎么设计的：行为与样式分层

gpui-kit 的核心哲学是一句话——**「行为属于地基，样式属于应用」**，对标 Web 世界的 Radix(headless) + shadcn(styled)：

| 层 | 名字 | 定位 |
|---|---|---|
| 入口 crate | **gpui-kit** | 单一依赖，re-export 下面全部并锁定匹配的 GPUI 版本 |
| 无样式行为内核 | **gpui-base** | 行为/状态/基建，无样式——给要做**自己设计系统**的团队 |
| 带样式组件 | **gpui-component** | 开箱即用、带主题的组件——给直接做应用的人 |
| 脚本运行时 | **gpui-shell** | Rust 托管的 JS 运行时，能力按需授权——给插件/脚本化应用 |

这样，团队可以**复用成熟的交互逻辑，再套上自己的皮**，而不必从「光标怎么闪、中文怎么输」重造。

#### 插一句：Radix / shadcn / Ant 到底是什么「约定」

上面反复提到对标 Radix 和 shadcn，这里补清楚这几个前端库各自代表的约定——gpui-kit 的分层正是把它们搬进了 Rust：

- **Radix UI = 无样式(headless)约定**。它只给你组件的**行为内核**：开合逻辑、键盘操作、焦点管理、无障碍语义——但**不带任何视觉样式**，长什么样完全由你决定。它还确立了**复合组件(compound components)**写法：一个 Select 不是一个黑盒，而是拆成 `Select.Root / Select.Trigger / Select.Content / Select.Item` 一组可自由拼装的零件。**gpui-base 对标的就是这一层。**
- **shadcn/ui = 「代码归你」约定**。它特立独行——**不是一个你 `npm install` 的依赖**，而是让你把组件源码**复制进自己项目**、从此自行拥有和改。它在 Radix(行为) 之上套一层 Tailwind 样式，于是你既白得了成熟行为，又能随便改样式，不受上游版本牵制。
- **Ant Design = 「开箱即用」约定**。另一个极端：**带一整套自家设计语言的成品组件**，`import` 进来就能用、风格统一、功能全，代价是**较重、改深度定制较难**。**gpui-component 对标的是这一端**——直接给做应用的人一套带主题、能跑的组件。

此外它们还共享两条通用约定，gpui-kit 也照搬了：**① 变体(variants)**——同一个 Button 用 `variant`(primary/ghost/danger) 和 `size`(sm/md/lg) 两个维度覆盖所有样式，而不是造出十几个按钮;**② 主题令牌(tokens)**——颜色/间距/圆角抽成一套语义令牌，换肤或明暗切换时整体生效。一句话：**Radix 管行为、shadcn 管「代码所有权」、Ant 管开箱齐全**，而 gpui-kit 用 `gpui-base`(headless) + `gpui-component`(styled) 把「可自定义」和「开箱即用」两头都占了。

## 结语

这一圈走下来，脉络很清晰：

- **Electron/Tauri** 用「开发快、生态全」换「性能有顶、架构割裂」，根因是把浏览器当 UI 层；
- **GPUI** 反过来，抛弃浏览器、自绘到 GPU，用「从零重造基建」换「原生性能 + 单语言统一架构 + 跨平台像素一致」；
- **gpui-kit** 则把「重造一切」的成本一层层摊平，让高性能跨平台桌面开发，从「只有 Zed 用得起」变成「更多人能坐下来就画页面」。

"Are we GUI yet?" —— 至少现在，有了一条认真可走的第三条路。
